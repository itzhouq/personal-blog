最近老觉得网慢。具体是一种很拧巴的慢：挂着代理还行，一关掉就难受——GitHub 打不开、Cloudflare 页面转圈、npm 装包要泡茶等。

我的应对方式也很原始：打开 Clash Verge，点测速，手动挑个延迟低的节点。一个机场不够就买了两个，慢了就切换订阅再来一轮。一个干了十年后端的程序员，天天手动给代理软件打工，这事儿越想越不对。

这次我没自己瞎猜，把整个过程丢给了 AI Agent，按「先定位、再动手」的顺序走了一遍。结果比想象中有意思：**网速慢是真，但一半的「慢」是我自己的工具和命令造出来的。**

## 第一步：先把问题边界测出来

AI 上来没急着改任何东西，先做了分层排查——内网、国内、国际，一层层过。

**内网层：干净。** 网关延迟 3.9ms、零丢包；WiFi 信号 -52dBm，空口质量很好。排除。

**国内层：健康。** 单线程 25~31 Mbps，延迟 32ms、零丢包。排除。

**国际层：问题在这。** ping 8.8.8.8 平均 993ms（正常应该 50ms 以内），GitHub 和 Cloudflare 直接断流。结论：公司出口的国际链路就是瓶颈，而且换 DNS 救不了——DNS 解析速度倒是顺手修了（从 114 换成阿里+腾讯双备份，解析从 20ms 降到 6ms），但那只是顺手，不是主因。

边界清楚了：**国内不慢、国际断流，所以解法只能是把国际流量从这条拥堵出口上挪走**——也就是把代理这条链路本身修好，而不是去优化直连。

## 第二步：测速这事儿本身就有坑

定位过程中 AI 还抓出一个我自己都没想到的问题：**我用的测速命令在撒谎。**

经典写法长这样：

```bash
curl -o /dev/null -s -w "%{speed_download}" --max-time 10 -r 0-20000000 <url>
```

下载 20MB，最多等 10 秒，报速度。拿它在手机热点上测，只有 506 KB/s，我一度以为蜂窝网就这样。AI 让我换个写法——不限时间，下载完再算——真实速度是 **10~14 Mbps，三倍多**。

问题出在参数组合上：蜂窝网络延迟高，TCP 慢启动要爬好几秒，10 秒一到下载被拦腰掐断，而 curl 报的是「已下载量 ÷ 时间」。**你在爬坡最陡的地方掐了表，当然觉得车慢。**

这一步给我的教训很大：边界测不准，后面全是白干。现在我的测速脚本有条铁律——必须校验 `size_download` 等于完整大小，不等于就作废重测。

## 第三步：抓出 Clash 里的三个潜伏者

边界定了，该修代理链路了。翻开两个订阅的配置，AI 逐条读完后报了三个问题，一个比一个离谱：

**一是「自动选择」一年四季在偷懒。** 我一直嫌这功能不好用，从来不碰它。但它的配置里躺着 `interval: 86400`——每 86400 秒测一轮延迟，**也就是一天一次**。我这一年手动测速挑节点，纯属替它上班。

**二是组里混着一堆假节点。** 「剩余流量：968.55 GB」「套餐到期：2027-03-03」「官网入口」「客户端下载提示」——这些是机场塞进订阅里的信息位，根本不是节点，但自动选择一视同仁拿去测速，结果能不歪吗。两个订阅加起来剔了 13 个。

**三是第二个机场常年吃灰。** Clash 一次只能激活一个订阅，我买的第二个机场基本是摆设，慢了才想起来切过去手动测一轮。

## 第四步：两个文件修完

**第一个是全局扩展脚本。** Clash Verge Rev 有个「全局扩展脚本」，会在任何订阅加载后跑一遍。往里面塞了一段 JS，核心逻辑几行：

```javascript
// 5 分钟一轮，自动挂最低延迟；80ms 内不切换，防抖
groups.unshift({
  name: "⚡ 极速线路",
  type: "url-test",
  proxies: realNames,        // 已过滤假节点
  url: "http://www.gstatic.com/generate_204",
  interval: 300,
  tolerance: 80,
  lazy: true,
});
```

**第二个是订阅合并。** 写了个 Python 脚本：拉两个订阅 → 过滤假节点 → 合并去重 → 生成一个 **67 个真实节点**的本地配置，自动选组横跨两个机场，谁快挂谁。再配个每天早上 8 点的定时任务自动刷新，节点有变化才弹通知。从此测速、切订阅这两件事从我的日常清单里删除。

## 最终验证：数据说话

修完跑了一轮同口径对比（都是完整下载法）：

| 指标 | 优化前（直连） | 优化后（走代理） |
|---|---|---|
| Cloudflare 10MB 下载 | 93 B/s，基本断流 | 5.0 Mbps，稳定 |
| GitHub 11MB 源码包 | 打不开 | **42.8 Mbps，2 秒下完** |
| 国内带宽 | 31~42 Mbps | 50 Mbps（没被拖慢） |
| 国内延迟/丢包 | 32ms / 0% | 31.7ms / 0% |

国内反而还快了一点，那不是配置的功劳，是时段差异——但至少确认规则分流没有拖累国内流量，该直连的直连。

**6700 倍是怎么算的**：Cloudflare 下载从 93 B/s 修到平均 625 KB/s（5.0 Mbps），625475 ÷ 93 ≈ 6725，标题里取整。GitHub 那条更夸张——优化前是彻底断流（0 B/s），数学上没法算倍数，只能说是「从 0 到 43Mbps」。倍数听着吓人，本质是「从不可用变成可用」，这才是这次修复真正的价值。

## 最后说说 AI 在这件事里的角色

复盘整个下午：分层排查是 AI 设计的，测速命令的坑是 AI 抓的，Clash 配置是 AI 逐条读完后指出来的，修复脚本和数据验证也全是它跑的。我的角色只有一个：**知道哪里不舒服，以及最后拍板用哪个方案。**

这也是我这半年用 AI 搞副业最大的感受：别攒问题。网速慢忍了半年，真正解决只用了一个下午，而且解决的比我自己上手干净得多——我不会去读 Clash 的完整配置，但 AI 会，还顺手把方法论沉淀成了脚本。**遇到不舒服的事，先让 AI 帮你把「模糊的烦」变成「可验证的问题」，再决定要不要自己上。**
