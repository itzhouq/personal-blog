先说背景：我在业余时间运营一批内容站（这个博客是主站，另外还有一批游戏攻略站），每站的状态分散在 Google Search Console、Cloudflare Analytics、广告后台，外加一个自己维护的 markdown 站况总表。表的列是这样的：站点、上次拉数日期、上次内容更新日期、下一步动作。每周五"数据日"逐站走一遍流程：拉数据 → 分析 → 改内容 → 提交收录 → 回填表格。

这套流程跑得动，但有两个体验很差的地方：

1. **"该干嘛"散落在表格的文本里**。哪个站超过 14 天没拉数、哪个站的热词窗口要过期，靠人肉扫表格；一忙起来就漏。
2. **每天开工要先开四五个后台**才能拼出"今天站况如何"。

最近「个人工作台」这个词很火——OpenClaw 一类的自托管 AI 助手刷屏，身边不少朋友在折腾。我认真评估过，最后没跟那个方向，而是用更笨的办法给自己钉了一面「站况墙」。这篇文章讲清楚：为什么这么选、墙怎么搭的、以及为什么它连截图都不能发。

## 为什么没跟"个人工作台"那波热点

OpenClaw（前身 Clawdbot）这波确实凶：自托管、7×24 在线、接微信 Telegram、有记忆能主动干活。形态我很认同——它本质上就是一个本地优先的 agent 运行时。但把它接进我的站运营，有两个过不去的坎：

**安全模型不匹配。** 这类平台的凭证是明文放本地目录的，已经出了多起实测泄露案例，国家互联网应急中心（CNCERT）在 2026 年 3 月都发了风险提示。而我的账本里是什么？热词库、选品结论、各站收益、未来三个月的内容排期——这些数据泄露的代价不是"换个密码"，是**我的生意被人原样抄走**。

**权限模型太粗。** 一个能读我全部文件、能执行命令的常驻 agent，和我需要的"每 15 分钟读一次 markdown 表格渲染出来"之间，能力差了三个数量级。给我递锤子可以，但我不需要住在工具箱里。

所以结论是：**要的只是"一面墙"，就不该引入一个"管家"。** 管家型工具我留了一个隔离的试用位（干净环境、不碰账本），那是另一篇文章的事。

## 墙的选型：Glance

自托管面板我看了 Homarr、Homepage、Glance 三个主流选项，选了 [Glance](https://github.com/glanceapp/glance)：

- **单二进制，零依赖**。Go 写的，下载一个文件就能跑，配 launchd 开机自启，没有 Docker 也没有 Node；
- **配置即代码**。整个面板是一个 YAML 文件，git 里一存，换设备就是 clone + 一条引导脚本；
- **有 `custom-api` 部件**：给我一个 JSON 端口 + 一段 Go template，就能渲染任意自定义数据。这是整个方案的关键榫头。

面板本身的能力（站点在线监控、RSS、书签）都是现成部件，没什么可说的。真正值得注意的是下面这个设计决策。

## 核心决策：账本是唯一真相源，墙只是视图

最偷懒的做法是把面板当成第二个"状态存储"——在面板上维护站点列表、更新日期。这条路一旦走下去，就是两份状态互相漂移的经典悲剧。

我的做法反过来：**什么都不在面板上写，所有状态仍然只活在那个 markdown 总表里**（它在私有仓库里随 git 三台机器同步，是唯一真相源）。面板只是它的视图：

```
markdown 站况总表 ──每 15 分钟──→ 桥接脚本(8091) ──JSON──→ Glance 面板(8080)
       ↑                                                    │
       └────── 改状态只改这里（git pull 自动进来）              └── 只读渲染
```

桥接脚本是个两百行以内的 python 标准库 HTTP 服务，干三件事：解析 markdown 表格、计算"距上次拉数/上次更新多少天"、按"最久没动"排序后吐 JSON。任何请求都实时重读文件——所以我在任何一台机器上 `git pull` 完账本、回填完数据，15 分钟内这面墙自己就对齐了，**不需要任何同步机制**。

第一屏的表格长这样（结构示意，真实面板的截图不能给你看，原因见最后一节）：

```
维护节奏 · 点击站名直达 GSC
站点              拉数      更新      下一步动作
site-a            1 天前    4 天前    例行；收录欠账 6 条已清账…
site-b            1 天前    0 天前    Adsterra 已接入（今日）…
site-c            无记录    6 天前    在其他设备维护，下次同步盘点…
```

几个值得展开的细节：

**1. 第一屏不是监控曲线，是"该干嘛"。** 我最初放的是所有站的在线状态，后来意识到：站挂了我从 GSC/Cloudflare 那边也会知道，而"哪个站 14 天没拉数了"只有我自己知道。所以排序逻辑是"最久没动的排最前"，阈值到了就变色——8 天黄色、14 天红色（14 天是我自己定的纪律线：超过就优先处理）。面板的价值不是"好看"，是把我的自律外包给一面墙。

**2. 站名直接深链到该站的 GSC。** `search.google.com/search-console?resource_id=sc-domain:example.com`，点击直达该站后台，省掉"打开 GSC → 在十几个资源里找"这两步。高频动作省一步，一周省几十次。

**3. 热词窗口单独一块。** 内容站有"版本更新后 48 小时内发布"的窗口期规则，过期词等于白写。词库里"已排期"的词会以到期队列的形式出现在墙上：超窗/今天到期标红，两天内标黄。排序在前面的就是今天必须动的。

**4. 红灯纪律：不监控需要代理才能访问的东西。** Cloudflare 后台、GitHub 这些域名在我的网络环境里直连必超时，如果给它们放监控徽标，墙上会常年挂着两个假红灯——红灯看多了人就不信红灯了。所以墙上只监控内容站本身（这些站点直连可达），平台后台一律只留书签。**仪表盘里最贵的东西是可信度，宁可少放不能掺假。**

## 多设备：一条脚本的理由

这面墙跑在 Mac 上，用 launchd 托管两个服务（面板 + 桥接脚本），开机自启、崩溃自动拉起。第二台 Mac 接入时我没有走 rsync 直拷——launchd 的配置文件里全是绝对路径，拷过去就是定时炸弹。做法是把 launchd 配置模板化（`__DIR__` 占位符），写了个幂等的 `install.sh`：自动检测架构、下载二进制（自动探测本机系统代理端口走 socks5，失败降级直连）、从模板渲染配置、加载服务、自检三个端口。新设备上就是 clone + 一条命令。

顺手记两个这次踩的、以后肯定还会遇到的坑：

> **bash 里 `$VAR` 后面紧跟中文全角括号会出事。** `echo "（$DIR）"` 这种写法，bash 会把全角字符的一部分当成变量名的一部分，报"unbound variable"，而且报错信息里根本看不出问题在哪。修法是永远写 `${DIR}`。

> **配置字段改名时旧字段会被静默忽略。** Glance 某个大版本把监控部件的字段从 `site-list` 改成了 `sites`，我的旧字段不报错、不告警，就是渲染出一个空列表。排查了半天配置逻辑，结果问题在版本差异。教训：升级之后"看起来在跑"的部件要逐个过一眼数据。

## 数据的墙：什么上墙，什么不上墙

这里是这篇文章真正想说的事。我的公开数据有三层纪律：收入到账总额、粉丝数这类**按节奏公开**；单站明细数据、热词、选品结论这类**延迟三个月公开**；订单、渠道这类**永不公开**。

这面墙本身跑在本机、只绑 127.0.0.1，属于最私密的一层——所以热词、站点清单、下一步动作的原文都可以放心放上去。但**这篇文章属于公开层**，一旦我放一张面板截图，就等于把"哪些站、域名是什么、每个站的运营状态和下一步计划"整张底牌拍在桌上。所以你在这篇里看到的是结构示意而不是截图，站名一律用 site-a 代替。

这不是戏剧化的安全焦虑，就是一个简单的判断题：**把这张图发出去，竞争者复制我的难度下降了多少？** 答案是"下降非常多"，那就只写经验、不发图。工具可以开源，打法不能。

## Roadmap

下一步有两个方向：

1. **从"墙"到"运营台"**：现在的墙是只读的。真正的高频动作（请求收录、拉数）还是要切回终端跑脚本。我计划把这些聚合成一个可部署的 Web 运营台——首屏三个模块已经定稿：跨站节奏表（带 GSC 数据摘要）、热词到期队列、收录动作区。验证稳定后会开源，面向的就是同时运营多个内容站的独立站长；
2. **管家型工具的隔离试验**：OpenClaw 那一路到底值不值得用，我会开一个干净环境试水，写一篇《为什么我没让它碰我的站矩阵》——如果它真的一次性把安全模型做扎实了，我也会说它好。

墙这套东西本身（Glance 配置、桥接脚本、引导脚本）目前私有，等运营台开源时会作为案例一起整理。如果你也在折腾个人工作台，欢迎交流，踩坑清单我会持续更新在这篇的评论区。
