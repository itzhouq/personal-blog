Hello [Build in Public](/blog/hello-build-in-public) 的第三周。这周折腾的事：攻略站挂的 Adsterra 广告，接入和数据两头的"人工味"都太重了，花了一个晚上把它改成了全自动。这篇把完整过程和踩的坑写下来。

## 痛点：两件"小事"每周都在烧钱

先交代背景。我有一批游戏攻略站，挂了 [Adsterra](https://www.adsterra.com/) 的广告（Banner 和 Native Banner，坚决不碰 Popunder——站上还有 AdSense，背后弹页会违反投放政策）。之前的工作流是这样的：

**接入一头**：每次给新站挂广告，都是 AI Agent 用浏览器自动化进 Adsterra 后台——打开网站列表、找目标站、点开单元、点 Get code、从弹窗里把广告代码挖出来。一轮下来浏览器快照刷了几十屏，token 哗哗地烧。这还没算进后台手滑点错的风险。

**数据一头**：广告挂上去之后，"到底赚没赚到钱"要等一两天，再开一次后台看 impressions；然后手动把数字记进账本，再重新生成公开的数据大盘。这套动作全靠我记着做——结果就是[数据大盘](/dashboard)经常是旧的，公开承诺打了折扣。

两件事本质是同一个病：**流程里有人肉环节，人肉环节必然不及时**。

## 调研：官方有 API，但要先认清它的边界

第一反应是老一套：先查有没有官方 API，别急着写浏览器自动化。还真有——Adsterra 有 Publisher API（v3），文档在 [docs.adsterratools.com](https://docs.adsterratools.com/public/v3/publishers-api)。

这里插一个通用技巧：这个文档页是个 Stoplight 单页应用，直接抓 HTML 什么都拿不到。但它本质是个壳，OpenAPI spec 是作为静态文件加载的——翻一下页面加载的 JS chunk，就能找到 spec 的真实路径（`/docs/public/v3/publishers-api.yml`），一条 curl 下来拿到了完整的官方接口定义：5 个端点、参数、响应结构、错误码，全部齐了。

API 的能力边界也清楚了：

| 能做（GET-only，只读） | 不能做 |
| --- | --- |
| 列出账号下所有网站和广告单元 | 添加网站 |
| 按日/站/单元/国家拉 impressions、点击、CPM、收益 | 创建广告单元 |
| SmartLink 列表 | **拿到广告单元代码** |

最后一条是关键：广告单元的代码（那段 `atOptions` 配置和 `invoke.js` 地址）不在 API 的任何响应里。也就是说，"全程无浏览器"做不到——**但这不是二选一的问题**。真正的解法是把浏览器从"每次都要开"降级成"白名单三件事"：加站、建单元、取码。一个站的一生，这三件事各只发生一次；之后的盘点、验证、看收益，全是 curl。

改造后还真有惊喜：账号下二十来个站、五十来个单元，两条命令全量盘点完，而且横幅单元的命名直接就是尺寸（`728x90_1`、`300x250_1`），连"这个单元是多大"都不用进后台确认了。取到的代码落盘到站点仓库的文档里，下回给同一个站加广告位，直接引用，后台一次都不用开。

## 设计决策：几条带理由的取舍

**1. 数据真相源只有一个文件。** 我之前搭过一套"账本 → 双层渲染"的体系：一个私密的 JSON 账本，生成器从它产出两样东西——本地开的私密大盘（全量数据）和博客公开页用的裁剪版 JSON。这次没有为广告收益新造一个面板，只是给账本加了一个 `income-adsterra` 指标。管道已经在那儿，接进去就完了。新造轮子一时爽，两套数据源之后对不上账才是真麻烦。

**2. 收益明细不公开，公开的只有折算合计。** 公开页拿到的永远是"总收入"一个数，哪个渠道赚多少属于账本的私密层。这是我自己定下的公开承诺：不夸张、不虚构、可复盘——口径本身写进了数据文件的 meta 里，跟着数据一起公开。

**3. 赚得和到账是两回事，先声明再上数。** 广告平台的报表收益是"赚得"口径，实际打款有起付线（Adsterra 是 $100）和账期。这个差别必须写在公开口径里，不然大盘上的数字就是在制造误解。

**4. token 读取链：`--参数` > 环境变量 > 仓库 .env > `~/.keys/` 密钥文件。** 这里有个值得单独说的弯路——

## 被自家红线拦下来的那个弯路

API 要认证，token 在后台生成。为了"零配置开箱即用"，我一开始把 token 直接写死在了脚本里，本机确实一步到位，很爽。

第二天把这个脚本往我的个人 skills 仓库推的时候，撞上了仓库 README 里自己写的安全红线：**API token 永不入仓，skill 内只写路径引用**。

推还是不推？把 token 一起推进私有仓库，"就这一次，反正是 private"；把红线绕过去，下个月就有第二个"就这一次"。红线的意义恰恰是拦住说"就这一次"的自己——所以改方案：token 挪进 `~/.keys/`（权限 600），脚本按上面那条读取链解析。本机依然是零配置（密钥文件在就行），仓库里一行密钥都没有，推送前还加了一道密钥残留扫描。

后来这条读取链还救了我一次：把 token 从脚本里删掉之后，同一台机器上所有依赖这个脚本的自动化（定时任务、数据回填脚本）一行没改，照常跑通。

**5. 调度避开数据的T+1 滞后。** 广告平台的统计有约一天延迟，当天的数据第二天才齐。所以定时任务设在每周一早上：拉"上个自然月（已定稿）+ 当前月（覆盖刷新）"两个月，跑完自动入库、重新生成大盘、部署、验证，最后给我一句话汇报。选周一还因为周一是新一周的开始，周末刚走完的完整一周数据正好看。

## 现在的工作流

接入一个新站：

```
API 盘点（网站 + 单元清单，零浏览器）
  → 单元都建齐了？直接从落盘文档拿码
  → 缺码才进一次后台（白名单三件事）
  → 取到码立即落盘复用
```

看收益：不用做了。每周一早上自动跑这一串：

```
拉 API 日收益按月求和 → 回填账本 → 重新生成大盘
→ 两仓库 git 入库 → 部署 → curl 验证线上 → 一句话汇报
```

上线十天，全账号的广告收益是个位数美金——不多，但从这一天起，[大盘](/dashboard)上的这个数字每周都会自己长，失败了我也会发。这才是 Build in Public 该有的样子。

## 复盘清单：这次学到的通用教训

给以后的我（也给你）：

1. **写浏览器自动化之前，先查官方 API**。很多 SaaS 有文档上不显眼的只读 API；文档页是 SPA 抓不到内容时，去翻它加载的 JS chunk，spec 文件的路径一般就在里面。
2. **实测报文和文档示例可能不一致**（错误体的结构就跟我拿到的 spec 示例对不上）。错误处理按 HTTP 状态码走，别解析报文结构。
3. **代理结论不能跨通道迁移**。同一台机器，A 服务必须挂代理，B 服务挂代理反而直接失败——这种事只能逐个通道实测，然后把结论写在通道自己的文档里。
4. **便利性和红线冲突时，把红线做成机制**（密钥文件 + 读取链），而不是给它开口子。开过的口子一定会被复用。
5. **公开数据的口径要写进数据文件本身**，跟着数据一起走。靠文章或者记忆维护口径，早晚会漂移。
6. 顺带一个广告位验证的坑：无头浏览器会被 Adsterra 反自动化拦截（请求直接 0/403），那是官方检测，不是你的接入坏了——出量验证以 API 统计为准。

## Roadmap 和相关链接

- **取码环节**：等官方哪天开放写接口，浏览器白名单就能清零；短期方案（取码落盘复用）已经把后台用量压到每站一次。
- **按站拆收益**：现在是全账号合计，先跑一阵看看有没有按站公开的需求。
- **账本 → 双层渲染这套**（私密全量 + 公开裁剪的自动管道）用起来比想象中顺，考虑整理成一个可复用的模板开源出来。
