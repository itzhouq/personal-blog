[搞副业的老周itzhouq的工具箱](https://tools.itzhouq.cn) 今天上线了：14 个解决日常小麻烦的在线工具，全部在你的浏览器本地运行，不上传任何数据。代码开源在 [GitHub](https://github.com/itzhouq/web-tools)。

这篇照例是复盘：为什么做、怎么取舍的、有哪些值得一提的设计，以及"一个代码库、两种域名形态"的上线方案。

## 为什么自己做

起因很日常：压缩一张图片、解析一个 JWT、生成一个二维码、写条文案想知道会不会踩违禁词——每件事都不难，但每次都要现去找在线工具。找来的工具体验参差：有的塞满广告，有的把你的文件悄悄传到服务器，还有的用两次就要收费。

其实这些活儿浏览器自己就能干：Canvas 能压缩和排版图片，JSON.parse 能校验数据，词典匹配能查敏感词。既然博客已经有了 Cloudflare Pages 的部署体系，顺手给自己搭一个趁手的工具箱，成本并不高。

更重要的一条底线：**所有工具纯前端实现，数据不出浏览器**。图片、文案、Token 这些东西凭什么要传给陌生服务器？

## 架构取舍

### 纯前端，零后端

第一个决定：不做后端。所有逻辑跑在浏览器里——Canvas 处理图片，`JSON.parse` 校验数据，本地词典扫敏感词，`qrcode` 库画二维码。

好处是三层叠加的：隐私零顾虑（卖点可以直接写进页脚）、运维零成本（没有服务器就没有监控和告警）、部署最简单（静态导出扔给 Cloudflare Pages 就完事）。代价是有些功能做不了——比如需要服务端计算的图片格式深度转换，或者需要登录态的跨设备同步。对这个工具集来说，这些都可以不要。

### Next.js 静态导出 + 注册表模式

技术栈和博客保持一致：Next.js 16 + Tailwind CSS 4，`output: "export"` 纯静态导出。

最值得说的一个设计是**工具注册表**：所有工具的元数据（slug、名称、描述、分类、图标、关键词）集中在一个 `lib/tools.ts` 里，首页的分类网格、搜索过滤、sitemap 全部从它派生。新增一个工具只有三步：

1. 在注册表里加一条元数据；
2. 写一个客户端组件；
3. 加一个路由文件引用它。

首页、搜索、SEO 自动生效，不需要碰任何展示层代码。以后加工具的边际成本非常低——这正是"工具集"和"一堆散落页面"的区别。

### 几个实现细节

做精致的工具比想象中难，几个细节：

- **中文换行**：Canvas 的自动换行对 CJK 不友好，`fillText` 一行直接溢出。手写了逐字符的换行算法，配合 `measureText` 按像素宽度断行，中英文混排都不会破版。
- **标题自适应**：封面工具的主标题最多 4 行，字号从 130px 起自动按行数收缩，保证填多长的标题都不溢出画布。
- **违禁词词典**：不是简单罗列词，而是按风险类型分成 6 类，每条词带修改建议，汇总成风险分级（高/中/低），高亮渲染在原文案上——用户要的不是"有 5 个违禁词"，而是"改成什么样能发"。

## 一个代码库，两种域名形态

上线时纠结过域名：独立子域名干净，但主域名子路径能吃主站权重。于是做了个双形态方案，同一份代码用环境变量切换：

```bash
npm run build            # 默认：部署到子域名
NEXT_PUBLIC_BASE_PATH=/tools npm run build   # 子路径：资源引用带 /tools 前缀
```

静态导出的文件布局在两种模式下完全一致，只是 HTML 里的资源引用不同。子路径部署前跑一个小脚本把 `_next` 资源移到 `tools/` 前缀下，让文件布局与 URL 一一对应。

子路径的流量通过一个 30 行的 Cloudflare Worker 接入，按路径分流：`/tools/`、14 个工具页和站点资源转发给工具站，其余路径（比如博客自己的 `/tools/chat`）原样回源。两边互不干扰，博客不需要重新构建。

最后是子域名：Pages 项目绑自定义域时 API 一条命令搞定，DNS 记录没有权限自动创建，最后是在 Dashboard 里补了一条 CNAME——这也是整个上线过程中唯一没法自动化的一步。
