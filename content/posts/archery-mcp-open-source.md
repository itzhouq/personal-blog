[archery-mcp](https://github.com/itzhouq/archery-mcp) 是我这段时间用得最顺手的自研工具，今天开源了。这篇是复盘：为什么做、怎么设计的、开源前做了什么。

## 三个日常工作痛点

日常迭代业务系统时，有三件事反复消耗我：

**第一，test 和 prod 的表结构、索引不一致。** AI 编码助手写的代码和上线脚本，默认基于它"知道"的表结构——多半来自 test 环境或者它自己的想象。等上线前人工一比对，字段类型对不上、索引缺了，返工。

**第二，上线脚本靠人工比对环境差异来写。** 版本迭代要提交 DDL/DML 工单时，我得先去生产库把表结构捞出来、核对索引，再让 AI 照着写。流程能跑通，但每一步都是人肉传递上下文。

**第三，数据清洗需要生产数据的真实特征。** 有些版本要清洗存量数据，脏数据长什么样、字段里实际存了哪些取值、边界记录有多少——test 环境的种子数据根本呈现不出来。写清洗脚本全靠猜。

这三个痛点的共同解法是：**让 AI 在编码工作流里随时、只读地"看见"生产库**。

## 为什么不直连生产库

第一反应当然是给 AI 配一个直连数据库的 MCP。但生产库的直连凭据一旦交给 agent，权限、审计、脱敏就全没了—— agent 拿到的是一把万能钥匙。

而我们的 SQL 查询和上线工单本来就在 [Archery](https://github.com/hkadb/archery) 上管理：谁有权限查哪个库、能返回多少行、哪些字段要脱敏、上线 SQL 要过什么检查，平台全有。**那正确的路径就不是绕过平台直连，而是把平台的查询能力封装给 AI**——凭据是个人账号的、权限跟着账号走、查询留审计记录、返回自动脱敏。AI 只是多了一个"通过平台看生产库"的入口，而不是拿到了万能钥匙。

于是有了 archery-mcp：一个 Archery 的 MCP Server。

## 三个关键设计决策

**1. 查询目标在服务端锁定。** 启动时用环境变量固定实例、数据库和模式，工具调用时不接收这些参数——模型想切别的库，没门。牺牲了灵活性，换来确定性的安全边界：这个 MCP 就是"生产某业务库的眼睛"，别的不存在。

**2. SQL 策略完全下沉给 Archery。** MCP 侧不做 SQL 语法限制、不遮蔽返回数据、不设行数上限——所有策略以平台配置和账号权限为准，原样转发、原样返回。理由：本地过滤会制造"看起来安全"的错觉，两套规则并存只会互相打架，审计也会失去一致依据。

**3. sql_check 双路检查。** 内置一套本地静态规范（SELECT 驳回、UPDATE/DELETE 必须带 WHERE、不收存储过程、警告事务控制语句……），叠加 Archery 平台检查（`/api/v1/workflow/sqlcheck/`），合并给出"通过 / 警告 / 驳回"结论。平台检查不可用时优雅降级，本地结果照常返回。上线前让 AI 自己先过一遍检查，工单驳回率肉眼可见地降了。

现在的工具集：`list_tables`、`describe_table`、`query`、`query_history`、`sql_check`。46 个单元测试全部 Mock，不碰真实环境。

## 实际工作流长什么样

现在写版本迭代的上线脚本，流程变成了：

1. 跟 Claude Code 说需求："给 xx 表加一个状态字段并写迁移脚本"；
2. agent 自己调 `describe_table` 看生产的真实结构，调 `query` 抽样看数据特征；
3. 基于真实结构生成 DDL/DML；
4. agent 自己调 `sql_check` 预检，驳回项自己改，直到通过；
5. 我人工过目后提交 Archery 工单走正常审批。

人工比对环境差异这一步消失了，AI 写出来的脚本从"猜着写"变成了"看着写"。

## 开源之前：一次彻底的脱敏

这个项目最初是给自己用的，代码里到处是内部信息：内网域名、包名里的公司标识、写死的生产实例名和库名，测试假数据里也有业务痕迹。更隐蔽的一个坑是 **git 提交身份——所有提交的作者邮箱都是公司邮箱**，文件扫干净了历史也洗不掉。

开源前做了几件事，也可以当作一份 checklist：

1. **代码收敛**：删掉两个历史残留包，包名去掉公司标识，敏感默认值改成必填环境变量；
2. **全局替换**：内网地址、实例名、库名、业务表名、测试假数据，全部换成通用占位（`https://archery.example.com`、`prod-app-db`、`app_users`……）；
3. **重建 git 历史**：与其清洗两个提交，不如重开一个干净初始提交，提交身份换掉；
4. **加防线**：写了敏感词扫描脚本挂进 CI，`bloks`、内网域名这类模式一旦再出现，CI 直接红——防止以后"顺手一提交"把内部信息带回来；
5. **合规文件**：MIT License、README 顶部三声明（非官方 / 免责 / 安全模型）、SECURITY.md 私密漏洞报告渠道。

最难的不是改文件，是意识到**历史也是文件**。`git log` 里的公司邮箱、被删掉文件的历史版本，都在仓库里躺着。开源不是"删掉敏感文件再 push"，是"从零构造一个可以公开的仓库"。

## 后续

Roadmap 上最想做的：**跨实例 schema diff**——对比 test 和 prod 的表结构/索引差异，直接生成变更清单。这其实就是痛点一的完全体，也是同类项目没有的能力。
