先报个账：上周四，我手里 8 个游戏攻略站的文件总数从 139 涨到 187。一天之内新增 101 篇文章——54 篇直接发布上线，47 篇以草稿状态挂在仓库里。这 101 篇里，我亲手一个字一个字写的，只有 1 篇。

剩下的全是 AI Agent 写的。这篇就聊聊这套流水线怎么跑起来的：分工怎么切、质量怎么兜底、AI 哪些行为超出我预期，以及四个差点翻车的坑。

## 起因：文章数上不去的站

背景简单交代下。我有一批游戏攻略站，跑 SEO 和广告，属于副业矩阵里最不起眼但最稳定的那一层。这些站有个共同的死穴：**内容产能**。

一个攻略站要有起色，内容量得先过某个门槛。以前我的生产方式是：查资料 → 自己写一篇 → 构建部署 → 提交收录。一篇认真写的攻略文，从查证到上线小半天就没了。8 个站排队等喂饭，写到手软，站数还是上不去。

10 月 12 号我决定换打法：**单站单 Agent，一个 Agent 负责一个站的写作，主会话负责所有 Agent 管不了的事**。一次最多同时跑 2-3 个 Agent（这个数字是踩坑踩出来的，后面细说），跑完一批验收一批，再放下一批。

## 分工：我管边界，Agent 管写

这套流水线里我的角色只剩三件事：**划选题边界、守事实红线、管发布动作**。

选题边界：每个站缺什么内容，先由我根据搜索数据定范围——哪些页面值得建，哪些话题不允许碰。Agent 只在边界内干活，不做自由发挥。

事实红线：游戏攻略站最容易翻车的地方是编造。游戏机制、数值、更新内容，写错了轻则没人搜到，重则被玩家评论区当场处刑。所以规矩是：**每个说法要有官方来源；关键结论要两个独立来源交叉验证；只有单一来源的，必须在页面上显式标注「此说法仅见于 XX」**。Agent 交稿，我抽查来源，不是抽查文笔。

发布动作：构建、部署、提交搜索引擎、更新站况台账，全部由主会话统一做。Agent 只碰 markdown 文件，不碰部署。原因很朴素——同时几个 Agent 各自部署，出问题我根本不知道该找谁。

## 红线：不是它写什么我发什么

这批 101 篇里最值得说的是那 47 篇草稿。

按「双源可证」的标准，有一批选题被我否了：有的游戏机制全网只能找到官方一句话，有的页面想写的结论没有任何可验证的出处。搁以前，这些选题就直接扔了。这批我换了个处理方式：**降级成草稿落地**——官方已确认的事实照常写进正文，缺失的部分用 TODO 注释列成「转正清单」，页面顶部加一段「为什么这页还是草稿」，什么证据齐了就能转正。

还有一个容易忽视的细节：**负向断言**。攻略站经常要写「这游戏没有 X 功能」这种页面，搜这个词的人不少，但「没有」是个危险结论——官方下个版本加了怎么办？所以规矩是：写「没有」，必须写明排查依据是什么、这个结论到哪天为止。AI 很擅长把话说满，这套纪律就是专门治它的。

草稿还有一条暗规矩：草稿内的链接只能指向已发布页面。有个 Agent 交的稿里出现了草稿链草稿的死链，它自己检查出来改掉了——这是后话。

## 意外：Agent 比我想的自觉

跑了几批之后，出现了几个我没设计过的行为，比文章本身更有意思。

一个 Agent 交稿前自己做了覆盖检查，发现资料不够撑起计划中的最后一篇，**主动少写了一篇**，并在报告里说明原因。换人干这活儿，大概率会为了凑数硬写。

另一个 Agent 在写某个角色页面时，顺手去查了官方更新公告，发现游戏刚出了热修复补丁——这个信息全站都没有。它把新补丁的内容用进了当批的新文章，还提醒我旧页面需要保鲜。等于它不光完成了任务，还做了一次信息侦察。

还有抓死链那个。草稿链草稿这种问题，我原本打算验收时统一查，结果它自查自改了。

我的结论是：**Agent 的「自觉」来自任务描述里写得足够具体的要求**。我给每个 Agent 的指令里有验收标准、有红线、有「不确定就标注而不是编造」的原则，它们真的会照着执行。反过来，指令里没写的，它们一样会翻车——比如下面这四个坑。

## 坑：四个差点翻车的地方

**第一，并发上限是 2-3 个，不是越多越好。** 第一轮我一口气放出去 6 个 Agent，结果发现根本验收不过来——主会话要抽查每个 Agent 的来源标注，6 份稿件同时到，检查质量直线下降，后来重发了一批才补齐。Agent 便宜，我的注意力贵。现在固定 2-3 个一批。

**第二，静默失败最要命。** 有个站的推送命令写的是静默模式，本地看着成功了，远端根本没收到——构建没触发，页面 404 了才发现。还有一次，某个站目录里残留的旧环境变量文件被部署工具自动加载，污染了认证，报错信息完全指向别的方向。这两件事让我加了一条验收铁律：**部署之后必须 curl 线上页面确认，成功信号只认线上状态，不认本地输出。**

**第三，构建期校验是最后一道闸。** 有 4 处文章描述超过了模板的长度限制，被构建直接拦下。这其实是好事——这类超限如果靠人眼，一篇都查不出来。另外封面生成脚本只为没有图片字段的 empty 文章生成封面，Agent 交的稿里预填了图片字段，脚本就静默跳过了，一个封面都没出。工具链的每个「静默跳过」，都得先知道它存在。

**第四，草稿不进构建，收录也别提交。** 草稿页不会出现在线上，所以搜索引擎那边一条都不能提。这听起来理所当然，但批量操作的时候很容易顺手把草稿 URL 也提交了。我的台账里草稿和发布分两列记，提交收录前只看发布列。

## 账算下来

两天批次收尾后我做了次全矩阵审计，所有站点检查通过；那 47 篇草稿也确认了没有一篇漏到线上——线上 404 恰好是草稿不进构建的预期行为。

更有说服力的是后手：两天里往搜索引擎优先抓取队列里塞了 30 多条新 URL，两天后去对账，**39 条待收页面全部「已编入索引」**，连之前标记「状态未知」的几条都自愈了。文章上了线，Google 真的在吃。

成本方面，这些站本来就是零成本的静态站，Agent 写作消耗的是订阅额度里的 token，换来的是原来需要至少一个月的写作量。当然，账不能只算产出不算质量——抽查里毙掉的选题、标着「单源」待验证的结论，都是这套流水线里真实存在的瑕疵。它不是印钞机，是一个需要编辑盯着的内容车间。

想清楚了这一点，我的位置也定了：**我不再是最慢的那个写手，我是唯一能决定什么能发出去的人。**

## 接下来

这套模式的下一步，是把「内容车间」往上游和下游各延伸一段。下游是收录和曝光的观察——Google 每天给的抓取配额有限，怎么省着用在刀刃上，我攒了一些实测细节，下一篇打算就写这个。上游则是外链：调研了一圈目录站批量提交的打法，一套素材粘 50 个站的路子已经摸清，等这批内容的收录数据稳了就动手试。

做了效果如何，照例数据公开，成不成都发。
